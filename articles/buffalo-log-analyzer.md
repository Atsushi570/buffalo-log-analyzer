## 事の発端

事務所のWi-FiとDHCPが不安定でした。「時々切れる」「朝方が怪しい」という体感はあるものの、Buffalo AirStationの設定画面からログを落としても**6,000行のテキスト**が出てくるだけで、どこを見ればいいのか分かりません。

```
2026/09/03 04:03:36      DHCPC	 DHCPRELEASE on br0 to 192.168.0.1 port 67
2026/09/03 04:04:31      DHCPC	 bound to 192.168.0.16 -- renewal in 86378 seconds.
2026/09/03 04:05:19      DHCPC	 DHCPRELEASE on br0 to 192.168.0.1 port 67
...
```

grepと目視で追うのは限界があるので、可視化ツールを作りました。

**🔗 https://atsushi570.github.io/buffalo-log-analyzer/**
**📦 https://github.com/Atsushi570/buffalo-log-analyzer**

ただ、この記事の本題は「作りました」ではありません。**作った診断ロジックが5箇所も間違っていて、それを指摘されて直した**話です。ログ解析ツールを作る人が同じ罠を踏まないように、間違いの中身をそのまま書きます。

## できたもの

### なぜブラウザ内解析にしたか

現場のログにはMACアドレス・端末名・内部IPが含まれます。これをどこかのサーバーに送るツールにすると、それだけで「業務で気軽に使えないツール」になります。ブラウザ内で完結させれば、社内のログをそのまま投入できます。

Chart.jsなども使わずSVGを直接組み立てているのは、CDNへの依存を減らして単一の静的サイトとして完結させたかったからです。棒グラフ・折れ線・ヒートマップ程度なら、SVGを手で書いても大した量になりません。

## 本題：診断ロジックが5回間違っていた

このツールの中核は「診断サマリ」です。単に件数を並べるのではなく、**何が起きているか・次に何を確認すべきか**を日本語で出します。

```
[重大] AP機: IPの解放と再取得を繰り返している
  148回、更新予定（T1 約24.0時間／推定リース期間 約2.0日）より極端に早く
  IPを再取得している（間隔の中央値 2分）。…うち148回は直前に自機が
  DHCPRELEASE（自発的なリース返却）を送っており、リースを失ったのではなく
  自ら返して取り直している。
  → 原因は上位側ではなくAP機自身にある可能性が高い。
```

（上記は初期表示＝直近24時間の集計。全期間で見ると149回・間隔の中央値3分になります）

これはLLMの推論ではなく、`src/analyze.js` に書いた**固定ルール**です。だからこそ、ルールが間違っていれば堂々と間違ったことを断言します。実際そうなりました。

### 誤り①：正常なメッセージを「重大」と報告していた

最初のバージョンは、こんなログに対して「**IPプール枯渇（重大）**」と出していました。

```
2026/09/01 15:52:13  DHCPS  Solicit message from fe80::8a55:... port 546
2026/09/01 15:52:13  DHCPS  Unable to pick client address: no IPv6 pools on this shared network
2026/09/01 15:52:13  DHCPS  Sending Advertise to fe80::8a55:... port 546
```

原因はこのコードです。

```js
// 悪い例
re: /^Unable to pick client address: (.+)$/,   // 理由を(.+)で捕まえたが…
severity: 'critical',
title: 'DHCPのIPアドレスプールが枯渇している'   // 中身を読まずに断定
```

**理由部分をキャプチャしておきながら、一度も参照していません。** メッセージの前半だけで判定していました。

実際の意味は「**ステートフルDHCPv6のプールが設定されていない**」です。`port 546`はDHCPv6クライアントポートで、IPv6をRA/SLAACで配る一般的な構成では**正常に出るメッセージ**。アドレスを配り切ったわけではありません。

証拠もはっきりしていました。同じ端末が**1秒後にIPv4を正常取得**しています。

```
15:52:14  DHCPDISCOVER from 18:93:41:8b:6d:9d via br0
15:52:14  DHCPOFFER on 192.168.0.71 to 18:93:41:8b:6d:9d (MSI) via br0
15:52:14  DHCPACK  on 192.168.0.71 to 18:93:41:8b:6d:9d (MSI) via br0
```

さらに`no free leases`は全期間0件、`DHCPNAK`も0件。枯渇の兆候はどこにもありませんでした。

```js
// 修正後：「プール未設定」と「空きが無い」を別物として扱う
{ id: 'dhcps_no_pool', label: 'DHCPプール未設定', severity: 'info', noise: true,
  re: /^Unable to pick client address: no (IPv6|IPv4)? ?pools? on this shared network/ },
{ id: 'dhcps_pool_empty', label: 'IPプール枯渇', severity: 'critical',
  re: /^(?:Unable to pick client address: (?!no (?:IPv6|IPv4)? ?pools? on)|no free leases)/ },
```

### 誤り②：良性のエラーを「IP競合の兆候」にしていた

```
2026/08/26 11:49:32  DHCPS  Error on ARPING request: Interrupted system call
```

`Error`と書いてあるので「IPアドレスの重複確認に失敗＝IP競合の可能性」と報告していました。

`Interrupted system call`は**EINTR**、つまりシステムコールが割り込まれただけです。実ログの3件すべて、直後にDHCPのやりとりが正常完了していました。

```
157: Error on ARPING request: Interrupted system call
158: DHCPDISCOVER from 82:c9:1f:1d:c6:21 via br0     ← 直後に正常完了
159: DHCPOFFER on 192.168.0.68 to 82:c9:1f:1d:c6:21 via br0
```

:::message
**DHCPサーバーのログは、正常動作でも「エラーらしく見える」メッセージを出します。** `Error`や`Unable`という単語だけで重み付けすると、正常なネットワークを「重大な障害」と報告するツールになります。
:::

### 誤り③：T1をリース期間と誤解していた（2倍間違い）

これは記事的に一番面白い誤りでした。

```
bound to 192.168.0.16 -- renewal in 86400 seconds.
```

この`86400`を見て「リース期間は約24時間」と診断文に書いていました。「Buffaloのデフォルトは48時間じゃない?」と指摘され、調べたら**完全に間違っていました**。

ISC dhclientのソース（`client/dhclient.c`）にそのままの出力があります。

```c
log_info("bound to %s -- renewal in %ld seconds.",
      piaddr(client->active->address),
      (long)(client->active->renewal - cur_time));   // ← T1 であってリース期間ではない
```

出力しているのは`client->active->renewal`で、直後の`state_bound()`には`/* T1 has expired. */`というコメントがあります。T1の導出はこうです。

```c
if (!client->new->renewal)
    client->new->renewal = client->new->expiry / 2 + 1;   // T1 = lease/2 + 1
```

つまり**T1 ≒ リース期間の50%**（RFC 2131 §4.4.5）。`renewal in 86400`なら**リース期間は約48時間**で、Buffalo公式マニュアルの出荷時設定表にある`リース期間 … 48時間`と一致します。指摘が正しかったわけです。

決定的だったのは実ログの数値でした。正常時の更新間隔を測ると:

```
median normal gap: 86493秒 (24.03時間)   ← T1通りに更新されている
median renewal:    86388秒
ratio gap/renewal: 1.001
```

**T1=24時間で更新が発火している** → リース期間は48時間。診断文は「リース期間24時間」と述べており、事実として2倍ずれていました。

```js
// 修正後：T1と推定リース期間を区別する
t1Sec: t1,                                  // ログに出るのはこの値
estimatedLeaseSec: t1 ? t1 * 2 : 0,         // RFC 2131: T1 ≒ lease/2
```

### 誤り④：原因の帰属が正反対だった（これが最も実害があった）

ここまでの修正後、サブエージェント2体にレビューさせたら、**もっと深刻な誤りが出てきました。**

修正後もこう報告していました。

> [重大] AP機: DHCPリースが保持できていない
> 149回それより極端に早くIP再取得している。
> **上位機器との通信断、またはIPアドレス競合が疑われる。**
> → ルーター側のDHCPリース設定を確認する

検証したら、149回すべてがこのパターンでした。

```
2026/09/03 04:11:32  DHCPC  DHCPRELEASE on br0 to 192.168.0.1 port 67  ← AP自身が解放
2026/09/03 04:12:07  DHCPC  DHCPDISCOVER on br0 to 255.255.255.255 port 67
2026/09/03 04:12:07  DHCPC  DHCPACK from 192.168.0.1
2026/09/03 04:12:27  DHCPC  bound to 192.168.0.16 -- renewal in 86380 seconds.
```

`DHCPRELEASE`は**クライアントが能動的にリースを返却する操作**（RFC 2131 §4.4.6）です。リースを失った・奪われたのであればRELEASEではなく、リース切れ後のDISCOVERか`DHCPNAK`になります。

```
premature（早期再取得）: 149 / うち直前にRELEASEあり: 149  ← 全件
boundしたIPの種類: 192.168.0.16 のみ   ← 一度も変わっていない
DHCPNAK件数: 0
09/03のWIRED/BOOTイベント: 0           ← 有線断も再起動もその日は無い
```

IPは一度も変わらず、NAKもゼロ。**「IP競合」も「上位機器との通信断」も成立しません。** 実際に起きていたのは「AP自身が繰り返し自らリースを返して取り直している」ことで、原因はAP側にあります。

これが一番マズい誤りでした。**切り分けの方向をルーター側へ誤誘導する**からです。この診断を信じてルーターの設定を延々と見直しても、原因には辿り着けません。

```js
// 修正後：RELEASE起点かどうかで原因の所在を分ける
const selfReleased = releases.some(r => r.t > prev.t && r.t < bounds[i].t
  && bounds[i].t - r.t <= 300_000);
...
const mostlySelf = churn.selfReleasedCount >= churn.prematureCount * 0.8;

title: mostlySelf
  ? `${dev.name}: IPの解放と再取得を繰り返している`
  : `${dev.name}: DHCPリースが保持できていない`,
hint: mostlySelf
  ? `原因は上位側ではなく${dev.name}自身にある可能性が高い。…`
  : 'ルーター側のDHCPリース設定と…',
```

### 誤り⑤：証拠がないのに原因を断定していた

「Wi-Fiの再接続が短時間に繰り返されている → **電波が不安定**」と報告していました。

しかしこのログ、`Deauthenticated`も`Disassociated`も**1件も記録されていません**。

```bash
$ grep -icE 'Deauthenticated|Disassociated|Authentication failed' *.log
260903_site1_ap_logfile.log:0
260903_site1_router_logfile.log:0
```

つまり「切断」の証拠はゼロで、`Authenticated User`の再出現しか見ていません。Buffaloの`Authenticated User`はWPAの再キーや省電力復帰でも出るため、これだけでは電波不安定と断定できません。

しかも分布を見ると、全期間では**647回中508回（79%）が1台に集中**していました。AP側の電波環境が原因なら複数台に分散するはずで、この分布はむしろ端末個体の挙動を示しています。

```js
// 修正後：断定を避け、分布で切り分けを促す
detail: …
  + (concentrated ? `全体の${Math.round(topShare*100)}%が1台に集中している。` : `複数の子機に分散している。`)
  + (hasDeauthLog ? '' : `このログには切断(Deauth/Disassoc)が記録されないため、`
    + `切断を伴う再接続か、WPA再キーや省電力からの復帰による記録かは判別できない。`),
hint: concentrated
  ? '1台に集中しているため、まず該当端末の省電力設定・無線ドライバを確認する。'
  : '複数台に分散しているため、チャンネル干渉などAP側の電波環境を確認する。',
```

## 学んだこと

### 1. ログの「文面」で判定してはいけない

5つの誤りのうち3つ（①②⑤）が、**メッセージの文字列だけで重み付けした**ことに起因します。`Error`・`Unable`・`failed`という単語は、正常系でも普通に出てきます。

必要なのは:
- メッセージの**意味**を一次資料（RFC、実装のソース、公式マニュアル）で確認する
- **前後の文脈**を見る（直後に正常完了しているか？）
- **傍証**を取る（他に異常を示すイベントがあるか？IPは変わったか？）

### 2. 「結果」を「原因」として報告しない

NTPの名前解決失敗73回を、当初は「インターネット側との通信が切れている時間帯を示す」と断定していました。実際は73件中71件がDHCP解放直後の10分以内、**全件が同じ日**。DHCP再取得の副作用であり、原因ではなく結果です。

```
[注意] NTPの名前解決が一時的に失敗している
  …うち68回は10分以内に同期成功しており、一時的な失敗にとどまっている。
  → DHCPでの再取得と同時刻に集中していれば、NTP失敗は結果であって原因ではない。
```

### 3. 異常検出は中央値+MADを使う

余談ですが、異常な時間帯の判定には**平均+標準偏差ではなく中央値+4×MAD**（中央絶対偏差）を使っています。平均と標準偏差は異常値そのものに引っ張られるため、大きな障害が1件あるとしきい値が跳ね上がり、かえって検出漏れを起こします。

もう一つの落とし穴が「平常時の基準」です。何も起きていない夜間の空ビンを含めて中央値を取ると基準が0に張り付き、「**平常の326倍**」のような無意味に誇張された数字になりました。

```js
// 稼働しているビンだけを平常時とみなす
const active = vals.filter(v => v > 0);
const med = median(active);
const mad = median(active.map(v => Math.abs(v - med))) || 1;
```

倍率の表示にも上限を設けています。基準が小さいと倍率が独り歩きするためです。

```js
function ratioText(ratio) {
  if (ratio >= 20) return '・平常より大幅に多い';   // 「59倍」とは言わない
  return `・平常の約${ratio.toFixed(0)}倍`;
}
```

### 4. 診断ツールは「断定しない」設計にする

READMEにこう書きました。

> **診断結果は出発点であり、結論ではありません。** 気になる所見は必ず「元のログを確認する」で該当時刻の生ログを読み、文脈を確かめてください。

そのため、気になった時間帯の**生ログをそのまま読める**機能を入れています。診断が疑わしいとき、ユーザーが自分で検証できることが重要です。

## 結局、事務所のネットワークは何だったのか

ツールが示したのはこうです。

| 指標 | 平常時 | 2026/09/03 |
|---|---|---|
| AP機のIP再取得 | 1日1回 | **149回** |
| NTP名前解決の失敗 | 0回 | **73回** |

24時間ごとに更新されるはずのIPを、**中央値3分間隔**で解放・再取得していました。しかもAP自身がRELEASEを送っており、その日は有線リンク断も再起動もなし。**AP側でインターフェースの再初期化が繰り返されている**という結論です。

![機器ごとの比較](/images/buffalo-log-analyzer/02-charts.png)
*上：種別ごとの内訳（赤い帯が異常な時間帯）／下：機器ごとの比較*

機器間比較のグラフを見ると、AP機とルーター機が同時刻に同じ形で反応しているものの、起点はAPのRELEASEでした。もし最初の誤診断（「上位機器との通信断」）を信じていたら、ルーター側を無駄に調べていたはずです。

## おわりに

ログ解析ツールの本体は、正規表現ではなく**ドメイン知識**でした。パーサを書くのは半日ですが、「そのメッセージが本当は何を意味するか」を確かめるほうがずっと時間がかかります。

そして自分の書いた診断ロジックは、思っていたより間違っていました。指摘してもらえなければ、堂々と間違ったことを断言し続けるツールになっていたはずです。

- **ツール**: https://atsushi570.github.io/buffalo-log-analyzer/
- **リポジトリ**: https://github.com/Atsushi570/buffalo-log-analyzer

匿名化したサンプルログを同梱しているので、「サンプルログで試す」ボタンで実際の障害の様子をすぐ見られます。Buffalo以外のログ形式にも、`src/parser.js`の`EVENT_DEFS`に定義を足せば対応できます。

同じような誤診断のパターンをご存知の方、あるいは「このメッセージの解釈が違う」という指摘があれば、ぜひIssueで教えてください。
